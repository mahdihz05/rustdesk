# API بنر و سیاست نسخهٔ abritdesk

کلاینت ویندوز 1.5.1 برای دریافت بنر و سیاست نسخه آماده می‌شود. آدرس پیشنهادی API:
`https://abritdesk.ir/api/v1/client/windows`.
این آدرس در زمان ساخت Rust از متغیر `ABRIT_CLIENT_API` دریافت می‌شود؛ خالی‌بودن متغیر، قابلیت را غیرفعال نگه می‌دارد و مسیر قبلی اجرا می‌شود. هیچ رمز مدیریتی در کلاینت قرار نمی‌گیرد.

## قرارداد GET

کلاینت پارامترهای `platform=windows`، `arch=x64` و `version=1.5.1` را می‌فرستد.
پاسخ با `Content-Type: application/json` و حداکثر 64 KiB برگردد.
نمونهٔ کامل: [client-manifest.example.json](../res/abrit/client-manifest.example.json).
آدرس تصویر، لینک بنر و دانلود باید HTTPS و بدون userinfo باشند. گواهی TLS باید معتبر باشد؛ بررسی گواهی در کلاینت غیرفعال نمی‌شود.

| فیلد | کاربرد |
| --- | --- |
| `schema_version` | فعلاً عدد 1 |
| `revision` | شناسهٔ تغییر محتوا؛ در هر ویرایش جدید تغییر کند |
| `poll_interval_seconds` | پیش‌فرض 30؛ کلاینت مقدار را بین 5 و 300 ثانیه محدود می‌کند |
| `banner.enabled` | نمایش یا مخفی‌سازی بنر |
| `banner.revision` | در تغییر تصویر افزایش یابد، حتی اگر URL ثابت بماند |
| `banner.image_url` / `image_url_dark` | تصویر تم روشن و تصویر اختیاری تم تیره |
| `banner.title` / `subtitle` | متن یا نگاشت زبان‌ها مثل `fa` و `en` |
| `banner.link_url` | مقصد اختیاری کلیک روی بنر |
| `update.latest_version` | آخرین نسخهٔ قابل دانلود |
| `update.minimum_version` | پایین‌تر از این نسخه، استفاده مسدود می‌شود |
| `update.mandatory` | اگر true باشد، تمام نسخه‌های پایین‌تر از latest هم مسدود می‌شوند |
| `update.download_url` | لینک HTTPS بستهٔ همان نسخه یا صفحهٔ دریافت آن |
| `update.message` | پیام بروزرسانی برای زبان‌های مختلف |

نسخه‌های انتشار عددی با حداکثر سه بخش پشتیبانی می‌شوند؛ `1.3` و `1.3.0` برابرند و `1.10` از `1.9` بزرگ‌تر است. نسخهٔ آزمایشی دارای پسوند در این قرارداد پذیرفته نمی‌شود. حداقل نسخه نمی‌تواند از latest بزرگ‌تر باشد.

سرور باید پیش از تعیین minimum، فایل نسخهٔ موردنیاز را منتشر کند. نمونهٔ download_url یک جای‌نگهدار است؛ پیش از فعال‌سازی سیاست 1.5.1 باید به بستهٔ واقعاً منتشرشدهٔ 1.5.1 اشاره کند، نه بستهٔ تأییدشدهٔ قبلی 1.5.0.

## بروزرسانی در حین اجرای برنامه

هستهٔ Rust در GUI و فرایند سرویس، سیاست را مستقل بررسی می‌کند؛ Flutter هر ثانیه وضعیت هسته را دریافت می‌کند. بنر و سیاست با دورهٔ API و بدون Restart تغییر می‌کنند. تغییر revision تصویر، کلید کش تصویر را عوض می‌کند. هنگام خرابی تصویر، تصویر محلی نمایش داده می‌شود و فرم اتصال قابل استفاده می‌ماند.

سرور می‌تواند `ETag` بدهد؛ پاسخ 304 فقط وقتی محتوای قبلی موجود است پذیرفته می‌شود. در تغییر عکس/متن/سیاست، revision و ETag باید تغییر کنند. پنل مدیریت آینده این کار را خودکار انجام دهد. پاسخ GET می‌تواند عمومی باشد؛ عملیات ویرایش و بارگذاری باید احراز هویت مدیریتی جدا داشته باشد.

## رفتار آپدیت

- اختیاری: پیام در خانه و دکمهٔ بررسی در درباره نمایش داده می‌شود؛ کاربر می‌تواند «بعداً» را انتخاب کند. پیشنهاد با تغییر latest دوباره نمایش داده می‌شود.
- اجباری: صفحهٔ غیرقابل ردکردن با دانلود، بررسی دوباره و خروج نمایش داده می‌شود. بازکردن دانلود محدودیت را برنمی‌دارد؛ نسخهٔ اجراشده باید واقعاً به حداقل برسد یا سرور سیاست را اصلاح کند.
- دانلود فعلاً در مرورگر باز می‌شود؛ نصب خودکار یا اجرای فایل دلخواه از API انجام نمی‌شود. بستهٔ قابل حمل باید کامل جایگزین شود و نسخهٔ قبلی از سینی سیستم بسته شود.
- اتصال‌های جدید از UI، URI و مسیرهای هسته مجاز نیستند؛ اتصال‌های فعال ورودی و خروجی نیز با دریافت سیاست مسدودکننده پایان می‌یابند. Remote desktop، انتقال فایل، دوربین، ترمینال و تونل شامل این محدودیت هستند.
- با فعال‌بودن این API، بررسی و آپدیت خودکار محصول قبلی کنار گذاشته می‌شود تا فایل محصول دیگری دریافت نشود. مسیر نصب/ارتقای همین فایل جاری حفظ شده است.

## قطعی و پاسخ نامعتبر

طبق انتخاب کاربر، اگر هنوز سیاست معتبری دریافت نشده و اولین درخواست شکست بخورد، پس از پایان بررسی اولیه استفاده مجاز است. سیاست معتبر در تنظیمات محلی ذخیره می‌شود و به آدرس API وابسته است. اگر نسخه از minimum ذخیره‌شده پایین‌تر باشد، قطعی، timeout، JSON خراب یا TLS نامعتبر آن را آزاد نمی‌کند. بازیابی کش فقط از endpoint همان بیلد انجام می‌شود؛ تنظیمات سرور اتصال و شناسهٔ کاربر تغییر نمی‌کنند.

نسخه‌های قدیمی‌تر از کلاینت دارای این قابلیت، از API خبری ندارند. الزام آنها با تغییر JSON ممکن نیست. برای آنها، پس از بررسی سرور اتصال، باید مهاجرت یا کنترل نسخه در سمت سرور طراحی شود. این قابلیت جایگزین کنترل دسترسی و احراز هویت سرور اتصال نیست.

## آزمون و راه‌اندازی

تست‌های Flutter شامل بنر زنده، تغییر زبان/تم، لینک امن، آپدیت اختیاری، حفظ ورودی، صفحهٔ اجباری، عدم آزادشدن با کلیک دانلود، قطعی اولیه و حفظ سیاست پس از پاسخ خراب هستند. مدل بومی Rust شامل مقایسهٔ نسخه‌ها، minimum، mandatory، اعتبار لینک، محدودیت پاسخ، کش وابسته به endpoint و رفتار قطعی است. اکشن ویندوز این تست‌ها و Smoke واقعی برنامه را پیش از آپلود بسته اجرا می‌کند.

آزمون نهایی شبکه بعد از دسترسی سرور: تغییر عکس/متن در همان اجرای برنامه، ETag/304، حداقل کمتر/برابر/بیشتر از نسخهٔ نصب‌شده، پیام اختیاری، قطع API پس از اجبار، Restart در حالت اجبار، رد اتصال جدید و پایان اتصال فعال، نصب نسخهٔ جدید و رفع محدودیت. تا استقرار API، به‌روزشدن محتوا از سرور واقعی ادعا نمی‌شود.

## سطح تغییرات

منطق جدید در `src/abrit_policy/` و `flutter/lib/abrit/control*` و `live_banner.dart` قرار دارد. هوک‌های لازم: `core_main.rs` شروع نگهبان سرویس/GUI؛ `ui_interface.rs` وضعیت فقط‌خواندنی و Retry بدون تغییر ABI؛ `client.rs` و `flutter.rs` رد شروع اتصال؛ `client/io_loop.rs` و `server/connection.rs` پایان اتصال فعال و رد ورودی مستقیم؛ `common.rs` و `updater.rs` جلوگیری از آپدیت محصول قبلی هنگام فعال‌بودن API. در Flutter، `common.dart` مسیر مشترک اتصال را کنترل می‌کند، `desktop_tab_page.dart` میزبان صفحهٔ اجباری است، `desktop_home_page.dart` پیشنهاد اختیاری را می‌گذارد، `desktop_setting_page.dart` بررسی دستی را در درباره می‌گذارد، `abrit/home.dart` بنر را متصل می‌کند و `smoke.dart` منتظر پایان بررسی اولیه می‌ماند. نسخه در Cargo و Flutter به 1.5.1 افزایش یافت. پروتکل، مدل دادهٔ اتصال، تنظیمات سرور و اندازهٔ پنجره تغییر نکردند؛ بدون API فعال، مسیر قبلی برقرار است.
