## Application Root Cause And Fix

The workstation's extracted 1.0.0 GUI and installed 1.5.4 service used the same main IPC name but different executable paths. Main IPC correctly rejects a different canonical executable. The GUI repeatedly logged `ipc connection closed: reset by the peer`; its diagnostic returned `online_status_reply_failed`.

The password is generated by the host process, not Flutter. Without working IPC, Flutter's password cache remains empty and its `Generating ...` placeholder never receives the real password. The displayed ID can still come from cached local state, so it does not prove readiness.

When another AbritDesk installation exists, the portable executable now derives a private runtime namespace from its canonical path. Configuration, IPC, shared-memory names, window class and tray mutex are isolated. The outward brand, URI, installer and SCM identity remain AbritDesk. Installed execution and execution without a competing installation retain their ordinary identity. Installation commands do not create a private Windows service.

Separate files alone were insufficient: the upstream default ID is MAC-derived. The private profile is therefore seeded with a distinct random ID through checked configuration persistence, before lazy Config readers start. Initial profile loading is serialized across active processes. The valid profile is reused on restart; read-only diagnostic/version commands do not initialize it. The withdrawn Preview 2's invalid shared-ID namespace is not reused or overwritten.

Signed custom installation policy is loaded before runtime selection. IPC executable authentication, session checks, ACLs and TLS validation are unchanged. No application layout, color, font, menu, language, or visible branding source was changed. The C++ change only selects an internal Win32 class name matching the Rust runtime.

## Why A Source Run Is Red

Run `38633033469` remains **failure**, not retroactively green. Its native build, packaging, 27 Flutter tests, 11 focused Rust tests and seven Python tests passed. It stopped on a newly added assertion that a private profile must be absent after an identity query. That assumption was invalid: earlier legitimate owned codec/tray processes can initialize the profile before the query.

The corrected harness snapshots existence/hash before and after the query, compares the native and independently calculated namespace, and verifies the real private GUI, distinct IDs, password readiness and restart behavior. Run `38641183280` independently passed against the **unchanged compiled EXE/MSI artifacts**. `source-provenance.json` records both outcomes and the binary SHA. Publication happened only after that acceptance passed, through the owner's authorized GitHub CLI; the job token's earlier HTTP 403 was not represented as successful publication.

Preview 2 is explicitly marked superseded. The earlier intermediate run `38631258519` was canceled before publication during identity review. No published tag was moved and no existing release asset was overwritten.

## Remaining Server-Path Failure

The same new binaries were retested on independent Windows VMs. Both had working IPC and actual password readiness. Receiver `498201979` stayed alive with fresh diagnostics throughout the observation period. Sender `306589044` showed `ID does not exist`; no remote display/input was accepted. Both owned test installations were cleaned up successfully.

The public endpoint probe is independent of the application GUI. From external Ubuntu, all 12 fresh nonexistent-ID lookups carrying the expected licence key returned `LICENSE_MISMATCH`. From external Windows, 11 returned `LICENSE_MISMATCH` and one returned `ID_NOT_EXIST`. Both resolved the domain to `2.180.18.102`. UDP registration/heartbeats and TCP online queries passed during that external probe; earlier LAN public-IP probes also observed divergent registration visibility.

The private Ubuntu endpoint consistently accepted that same key for the corresponding lookup. Host inspection found one intended hbbs, matching startup/public-key-file values, no relevant environment override, no container/alternate namespace, no IPv4/IPv6 current or legacy firewall rules, no IPVS, and no relevant local proxy/BPF redirect. These observations support inconsistent public routing/backend service state, but do not identify a particular pfSense rule or cryptographically identify a legacy responder. The precise edge fault is still unconfirmed. Changing the client's trusted key or bypassing verification would be incorrect.

Cloudflare is authoritative DNS; this alone is not proof of a native RustDesk tunnel. No authorized pfSense/Cloudflare/internal-DNS administration is available. Internal management HTTPS still fails normal Windows trust validation against the self-signed origin, rechecked after the local password fix. Public HTTPS validated normally with a Let's Encrypt certificate, but its RSA public key differs from the origin's existing key; copying only that public certificate would not repair the origin. This route is separate from main RustDesk IPC/rendezvous. No TLS verification was disabled and no server identity key was rotated.

## Operational Incident

A quoting error in a host-inspection command accidentally launched an additional hbbr process, PID `102405`, at `2026-10-14T20:35:13Z`. It was not a preexisting alternate backend and did not listen on hbbs port 21116. After matching its executable and exact start time, only that investigator-created process was terminated. A subsequent check confirmed it was gone and relay ports were owned solely by original PID `5682`. The original hbbs PID `83420` and hbbr PID `5682` remained active with their original October 11 and September 20 start times. The public-path discrepancy was observed before this incident; the new desktop failure was measured after cleanup.

## Regression Surface

Existing runtime changes are confined to Windows identity initialization/classification and outward name resolution (`src/common.rs`, `src/core_main.rs`, `src/platform/windows.rs`), plus invisible Win32 class selection (`flutter/windows/runner/win32_window.cpp`). New logic lives in the Windows identity/portable modules. There is no final change to `src/server.rs`, no submodule change, and no Flutter/Dart design change. Test/workflow changes add password/coexistence assertions, correct profile snapshots, and verify exact binary provenance. The remaining lack of a successful public desktop session is not obscured by those passing tests.
